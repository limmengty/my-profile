Broken Access Control តែងតែត្រូវបានចាត់ថ្នាក់ជាចន្លោះប្រហោងសុវត្ថិភាព (Security vulnerability) ដ៏ធ្ងន់ធ្ងរបំផុតមួយដោយ OWASP។ វាកើតឡើងនៅពេលដែលកម្មវិធី (Application) មិនបានអនុវត្តការរឹតបន្តឹងឲ្យបានត្រឹមត្រូវទៅលើអ្វីដែលអ្នកប្រើប្រាស់ដែលបាន Login (Authenticated users) ត្រូវបានអនុញ្ញាតឲ្យធ្វើ។

> **សេចក្តីសង្ខេប (TL;DR):** កុំពឹងផ្អែកលើទិន្នន័យពីខាង Client (Client-side data) ដូចជា Query strings សម្រាប់គ្រប់គ្រងសិទ្ធិចូលប្រើឲ្យសោះ។ ត្រូវប្រមូលផ្តុំ (Centralize) Authorization logic របស់អ្នកនៅលើ Server, អនុវត្តការគ្រប់គ្រង Session (Secure session management) ឲ្យមានសុវត្ថិភាព, និងប្រកាន់យកផ្នត់គំនិត "បដិសេធជាមុនសិន (Deny by default)"។

## គ្រោះថ្នាក់នៃការគ្រប់គ្រងសិទ្ធិនៅខាង Client (The Danger of Client-Side Access Control)

កំហុសដ៏ទូទៅ និងមានគ្រោះថ្នាក់បំផុតមួយ (Anti-pattern) គឺការពឹងផ្អែកលើទិន្នន័យពីខាង Client — ដូចជា Query strings — ដើម្បីកំណត់ពីតួនាទី (Role) ឬសិទ្ធិ (Permissions) របស់អ្នកប្រើប្រាស់។ ឧទាហរណ៍ ការអនុញ្ញាតឲ្យ URL parameter ដូចជា `?role=admin` អាចផ្តល់សិទ្ធិជា Admin បាន។

ការប្រើប្រាស់ Query strings សម្រាប់គ្រប់គ្រងសិទ្ធិចូលប្រើ បង្កើតឲ្យមានហានិភ័យធ្ងន់ធ្ងរដូចជា៖

- **ងាយស្រួលក្នុងការកែប្រែ (Easy manipulation):** Query strings គឺអាចមើលឃើញ និងអាចកែប្រែបានដោយនរណាម្នាក់នៅក្នុង Browser។
- **ការបែកធ្លាយទិន្នន័យសំខាន់ៗ (Sensitive data exposure):** តួនាទី ឬកម្រិតសិទ្ធិនៅក្នុង URL អាចបែកធ្លាយតាមរយៈ Browser history, Server logs, និង Referer headers។
- **ការរំលងការត្រួតពិនិត្យ (Validation bypass):** វាអាចរំលងការត្រួតពិនិត្យសុវត្ថិភាព (Authentication checks) ដ៏ត្រឹមត្រូវនៅលើ Server ទាំងស្រុង។
- **បង្កើនឱកាសនៃការវាយប្រហារ (Increased attack surface):** Hacker អាចធ្វើសកម្មភាពដែលគ្មានការអនុញ្ញាតដោយគ្រាន់តែកែប្រែ URL parameters បន្តិចបន្តួចប៉ុណ្ណោះ។

## របៀបស្វែងរកចន្លោះប្រហោងនៃការគ្រប់គ្រងសិទ្ធិ (How to Identify Access Control Vulnerabilities)

ដើម្បីចាប់កំហុសទាំងនេះឲ្យបានមុនពេលយកទៅដាក់ឲ្យប្រើប្រាស់ (Production), អ្នកត្រូវដឹងថាគួរស្វែងរកអ្វីខ្លះនៅក្នុងកូដរបស់អ្នក។ ត្រូវប្រយ័ត្នចំពោះសញ្ញាព្រមានទាំងនេះ៖

- ការសម្រេចចិត្តផ្តល់សិទ្ធិដោយផ្អែកលើការបញ្ជាពី Client (Client-controlled inputs) ដូចជា Query strings, Form data, ឬ Headers។
- មិនមានការត្រួតពិនិត្យសិទ្ធិ (Authorization checks) ឲ្យបានច្បាស់លាស់ មុនពេលអនុញ្ញាតឲ្យធ្វើសកម្មភាពសំខាន់ៗ ឬចូលមើលទិន្នន័យ។
- ការចម្លងកូដ (Copy-pasted) សម្រាប់គ្រប់គ្រងសិទ្ធិ ដែលអាចមិនគ្រប់ជ្រុងជ្រោយ ឬហួសសម័យ។
- ការទុកកូដតេស្ត (Test-only shortcuts) ចោលនៅក្នុងបរិស្ថាន Production។
- សារជូនដំណឹងពីកំហុស (Error messages) ដែលបង្ហាញព័ត៌មានលម្អិតពេកអំពី Access control logic ខាងក្នុងរបស់អ្នក។

## ក្របខ័ណ្ឌនៃការទប់ស្កាត់ (The Prevention Framework)

ដើម្បីដោះស្រាយបញ្ហា Broken Access Control, អ្នកត្រូវតែប្តូររាល់ Authorization logic ទាំងអស់ទៅកាន់ Server វិញ។ ការពឹងផ្អែកលើទិន្នន័យបញ្ជូនពី Client គឺមិនមានសុវត្ថិភាពទាល់តែសោះ។

### 1. អនុវត្តការគ្រប់គ្រង Session ឲ្យមានសុវត្ថិភាព (Implement Secure Session Management)

Access control របស់អ្នកគឺមានសុវត្ថិភាពអាស្រ័យទៅលើការគ្រប់គ្រង Session របស់អ្នក។ នៅពេលដែលអ្នកប្រើប្រាស់ Login, ត្រូវកំណត់អត្តសញ្ញាណពួកគេដោយប្រើវិធីសាស្ត្រមានសុវត្ថិភាព៖

- រក្សាទុក Session identifiers នៅក្នុង Cookies ដែលមានសុវត្ថិភាព និង Encrypted ដើម្បីកុំឲ្យគេអាចអាន ឬកែប្រែបានដោយងាយ។
- កំណត់ Cookie attributes ឲ្យបានតឹងរ៉ឹង៖ **HttpOnly** (ការពារកុំឲ្យ JavaScript ទាញយកបាន), **Secure** (ប្រើសម្រាប់តែ HTTPS), និង **SameSite** (កាត់បន្ថយការវាយប្រហារ CSRF)។
- បង្កើត Session tokens ដែលរឹងមាំ និងមានទម្រង់ចៃដន្យ (Cryptographically random)។
- ត្រួតពិនិត្យ (Validate) Session token រាល់ពេលមាន Request ម្តងៗ ដើម្បីបញ្ជាក់អត្តសញ្ញាណ និងសិទ្ធិ។
- កំណត់គោលការណ៍ផុតកំណត់នៃ Session (Session expiration policies) ឲ្យបានតឹងរ៉ឹង និងផ្តាច់ Session ភ្លាមៗនៅពេល Logout ឬទុកចោលយូរ។

### 2. ប្រមូលផ្តុំការគ្រប់គ្រងសិទ្ធិ (Centralize Your Access Control)

ការចម្លងកូដ (Copy-pasting) Access control ដាក់តាម Modules ផ្សេងៗគ្នា ធ្វើឲ្យចន្លោះប្រហោងរាលដាល ពិបាកកែតម្រូវ និងស្មុគស្មាញក្នុងការគ្រប់គ្រង។ ជំនួសមកវិញ អ្នកគួរតែប្រមូលផ្តុំវា៖

- បង្កើត Access control module ឬ Service តែមួយដែលទទួលបន្ទុកត្រួតពិនិត្យ Authorization ទាំងអស់។
- ហៅ (Call) Module ដែលបានប្រមូលផ្តុំនេះមកប្រើរាល់ពេលដែលត្រូវការបញ្ជាក់សិទ្ធិ, ជាជាងការសរសេរកូដដដែលៗ។
- អាប់ដេតច្បាប់ (Rules) នៅកន្លែងតែមួយ ដើម្បីឲ្យវាមានប្រសិទ្ធភាពទូទាំងកម្មវិធីទាំងមូល។

### 3. រៀបចំប្រព័ន្ធ RBAC ឲ្យបានរឹងមាំ (Design a Robust Role-Based Access Control System)

សម្រាប់កម្មវិធីខ្នាតធំ ការគ្រប់គ្រងសិទ្ធិសម្រាប់ម្នាក់ៗគឺមិនអាចទៅរួចទេ។ ត្រូវអនុវត្ត RBAC ដោយធ្វើតាមជំហានទាំងនេះ៖

- កំណត់ Roles ឲ្យបានច្បាស់លាស់ផ្អែកលើការងារជាក់ស្តែង (ឧ. Editor, Manager, Support)។
- បញ្ជាក់ឲ្យច្បាស់ថា Role នីមួយៗអាចធ្វើសកម្មភាពអ្វីខ្លះ និងអាចចូលមើលទិន្នន័យអ្វីខ្លះ។
- អនុវត្តគោលការណ៍ **Least privilege** (ផ្តល់សិទ្ធិតិចបំផុត) ដើម្បីឲ្យអ្នកប្រើប្រាស់មានត្រឹមតែសិទ្ធិដែលចាំបាច់សម្រាប់ការងាររបស់ពួកគេ។
- ប្រើប្រាស់ឈ្មោះ Role ឲ្យបានច្បាស់លាស់ និងមានអត្ថន័យ។ ឈ្មោះដែលស្រពិចស្រពិលដូចជា "super admin" បង្កើតឲ្យមានការយល់ច្រឡំ នាំឲ្យមានការកំណត់សិទ្ធិខុស និងធ្វើឲ្យការធ្វើសវនកម្មសុវត្ថិភាពមានភាពស្មុគស្មាញ។

### 4. ប្រកាន់យកផ្នត់គំនិត "បដិសេធជាមុនសិន" (Adopt a "Deny by Default" Mindset)

អ្នកប្រើប្រាស់មិនគួរបើកមើលទិន្នន័យសំខាន់ៗបានទេ លុះត្រាតែពួកគេទទួលបានការអនុញ្ញាតច្បាស់លាស់។ ប្រសិនបើ Endpoint មួយមិនមានកំណត់ច្បាប់ Authorization ច្បាស់លាស់ទេ វាគួរតែបដិសេធ (Reject) Request នោះដោយស្វ័យប្រវត្តិ។

## ការរក្សាសុវត្ថិភាពរយៈពេលវែង (Maintaining Security Long-Term)

Access control មិនមែនជាមុខងារដែលធ្វើរួចហើយទុកចោលនោះទេ។ ដើម្បីរក្សាបរិស្ថានឲ្យមានសុវត្ថិភាព អ្នកត្រូវតែវាយតម្លៃប្រព័ន្ធរបស់អ្នកជាប្រចាំ។

សាកល្បងតេស្តកម្មវិធីរបស់អ្នកដោយព្យាយាមចូលមើលទិន្នន័យហាមឃាត់ ដោយប្រើគណនីដែលគ្មានសិទ្ធិ។ បិទរាល់មុខងារដែលមិនមានសុវត្ថិភាព ឬ Debug endpoints ដែលអាចក្លាយជាច្រក (Backdoor) សម្រាប់ Hacker។ ចុងក្រោយត្រូវប្រាកដថាអ្នកមានប្រព័ន្ធ Logging និង Alerting ត្រឹមត្រូវ។ បើគ្មាន Logs ត្រឹមត្រូវទេ ការព្យាយាមចូលលួចទិន្នន័យនឹងមិនមានអ្នកណាដឹងឡើយ ដែលធ្វើឲ្យការឆ្លើយតបនឹងបញ្ហានិងការធ្វើសវនកម្មសុវត្ថិភាពស្ទើរតែមិនអាចទៅរួច។
